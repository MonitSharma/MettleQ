# MettleQ SDK tutorials

These notebooks show the same local quantum workload twice: first with the
SDK's reference simulator, then through MettleQ on Apple Silicon. They are
written as lessons rather than benchmark scripts. Each notebook now contains:

1. learning goals and the relevant quantum-computing idea;
2. an explicit explanation of what the reference and MettleQ actually use;
3. a separate, readable problem-construction block;
4. a separately timed SDK reference block;
5. a separately timed MettleQ block;
6. a correctness check explained in domain terms; and
7. a human-readable performance conclusion plus a machine-readable
   `TUTORIAL_RESULT` record.

## What “matching” means

Quantum simulators do not always have a useful byte-for-byte comparison:

- analytic statevectors, probabilities, expectation values, and gradients are
  checked numerically with an explicit absolute tolerance;
- deterministic basis-state algorithms also require the exact same answer;
- finite-shot samples use independent random-number generators, so the
  notebooks report exact count-dictionary equality separately and require a
  bounded total-variation distance between distributions;
- MPS notebooks compare with an exact reference and expose MettleQ's accuracy,
  truncation, routing, and convergence evidence.

The timings are tutorial observations, not publication benchmarks. They include
the complete SDK call shown in the notebook, use a warm-up followed by repeated
runs, and deliberately retain cases where the reference is faster.

## Why `Exact? False` does not mean incorrect

`exact_match` records byte-for-byte equality. That is deliberately reported,
but it is not the numerical pass criterion. The Apple GPU statevector commonly
uses complex64 while the CPU references use complex128, so last-bit differences
are expected. Finite-shot devices also use independent random streams and
should not produce identical count dictionaries.

The executed audit passed all 29 notebooks: 9 were bit-for-bit matches and 20
were independently validated within their declared numerical or statistical
tolerance. The largest primary error used 0.408 of its allowed tolerance. See
[`correctness_audit.md`](correctness_audit.md), generated by:

```bash
python tools/audit_tutorial_correctness.py
```

## Why MettleQ is not faster in every notebook

Qiskit's statevector reference and PennyLane's `default.qubit` already execute
on the Mac's Apple CPU. The comparison is therefore not “Apple Silicon versus
no Apple Silicon.” MettleQ adds planning, SDK adaptation, dispatch,
synchronization, and result conversion. Those costs dominate tiny circuits.

MettleQ becomes interesting when exact state evolution is large enough for its
MLX/Metal GPU path to amortize that overhead. The tutorial scaling lesson uses
a simple educational reference. The stricter large-state experiment instead
uses Qiskit Aer statevector and MPS (selecting the faster CPU result) and
PennyLane `lightning.qubit`, then returns and validates the complete state:

| Width | Aer fastest CPU / MettleQ GPU | Lightning CPU / MettleQ GPU | Interpretation |
| ---: | ---: | ---: | --- |
| 16q | 0.255× | **1.445×** | Aer wins; MettleQ beats Lightning |
| 18q | 0.627× | **3.710×** | Aer wins; MettleQ beats Lightning |
| 20q | **1.327×** | **11.097×** | Qiskit crossover begins |
| 22q | **3.160×** | **16.429×** | MettleQ beats both CPU references |
| 24q | **4.554×** | **18.713×** | MettleQ beats both CPU references |
| 26q | **4.256×** | **19.229×** | MettleQ beats both CPU references |
| 27q | **3.561×** | **18.186×** | MettleQ beats both CPU references |
| 28q | **2.833×** | **21.177×** | MettleQ beats both CPU references |
| 29q | **2.739×** | **16.005×** | Largest guarded full-state match |

All eighteen cross-SDK states passed the phase-aligned full-state threshold;
the worst amplitude error was `4.02e-7` against a `5e-6` limit. On this M3 Pro
and workload, MettleQ crosses Aer around 20 qubits and stays faster through the
largest admitted 29-qubit full-state validation. The
plot, raw samples, protocol, and environment are in
[`assets/benchmarks-frozen/fork-m3pro-20260718-sdk-crossover-radix16-idle/`](../assets/benchmarks-frozen/fork-m3pro-20260718-sdk-crossover-radix16-idle/).
The 15-cell executed
[`large crossover experiment`](experiments/01_large_sdk_cpu_gpu_crossover.ipynb)
walks through the contract, raw timings, accuracy gate, chart, interpretation,
and reproducibility command without rerunning the multi-gigabyte workload when
the notebook is opened.

## Coverage boundary

The detailed per-category disposition is maintained in
[`COVERAGE.md`](COVERAGE.md).

This suite covers the locally simulatable, unitary circuit cores of the current
[IBM Quantum tutorial catalog](https://quantum.cloud.ibm.com/docs/en/tutorials/index),
the Qiskit [exact local simulation](https://quantum.cloud.ibm.com/docs/en/guides/simulate-with-qiskit-sdk-primitives)
and [V2 primitive](https://quantum.cloud.ibm.com/docs/en/api/qiskit/2.0/primitives)
contracts, and the foundational PennyLane material on
[QNodes](https://docs.pennylane.ai/en/stable/introduction/circuits.html),
[measurements](https://docs.pennylane.ai/en/stable/introduction/measurements.html),
and [gradients](https://docs.pennylane.ai/en/stable/introduction/interfaces.html).

The algorithm notebooks are compact local counterparts to the official
[CHSH](https://quantum.cloud.ibm.com/docs/en/tutorials/chsh-inequality),
[Grover](https://quantum.cloud.ibm.com/docs/en/tutorials/grovers-algorithm),
[Shor](https://quantum.cloud.ibm.com/docs/en/tutorials/shors-algorithm),
[PennyLane QFT](https://pennylane.ai/demos/tutorial_qft),
[PennyLane QPE](https://pennylane.ai/demos/tutorial_qpe),
[PennyLane VQE](https://pennylane.ai/demos/tutorial_vqe),
[PennyLane QAOA](https://pennylane.ai/demos/tutorial_qaoa_intro), and
[variational-classifier](https://pennylane.ai/demos/tutorial_variational_classifier)
tutorials. The implementations here are original, smaller examples designed to
exercise the MettleQ device contract; they do not copy those tutorials.

Hardware calibration, noise modeling, Runtime sessions, error mitigation and
detection, Qiskit Functions/Serverless, circuit cutting addons, live cloud
credentials, continuous-variable devices, mixed-state channels, and native
mid-circuit control are intentionally not presented as working MettleQ
features. A full copy of every web tutorial would be misleading because those
workflows require capabilities outside a local ideal statevector/MPS backend.

## Run the suite

Install the tutorial dependencies and execute every notebook from the repository
root:

```bash
python -m pip install -e '.[tutorials]'
python tools/build_tutorial_notebooks.py
python tools/run_tutorial_notebooks.py
```

The runner updates the executed notebooks in place and writes
`tutorials/results.json` plus `tutorials/results.md`. A failure in any numerical
or statistical assertion stops the run and returns a non-zero exit status.
